## Executive Summary

`packages/database` is now a real, working Prisma package with a single domain model (`Studio`), implemented against **two independent, fully generated Prisma Clients**: PostgreSQL (primary/production, for `apps/api`) and SQLite (local-development / future-desktop preparation, per ADR 0001).

Prisma had moved to **major version 7** since the M2 planning report was written, which changed the architecture materially (config file instead of schema-embedded connection URLs, a new Rust-free client generator, mandatory driver adapters). This report documents every resulting decision and every deviation from both the original frozen architecture and the M2 planning report, with justification for each.

Both schemas generate cleanly. The SQLite migration was authored and **applied for real** against a local file-based database — `prisma migrate status` confirms it is in sync. The PostgreSQL migration SQL was generated **fully offline** (no live PostgreSQL server exists in this environment); `prisma migrate status` against PostgreSQL correctly reports a connection failure, which is expected, not a defect.

The repository-wide `pnpm typecheck` still fails — but not because of anything introduced by M2. Section 9 below shows this is a pre-existing condition affecting 11 apps/packages that have contained no real source code since the original scaffold (M0), verified line-by-line in this session. `packages/database`'s own typecheck passes cleanly in isolation.

**Section 10 gives a direct answer on M3 readiness: yes, with two caveats**, both documented under Remaining Issues.

## 4. Every Prisma 7 Architecture Decision

The M2 planning report was written against Prisma 6/generic assumptions. The actually-installed version is **Prisma 7.8.0**, confirmed via `npx prisma --version`. This section documents every architectural fact about Prisma 7 that shaped the implementation, each verified directly against the installed CLI/packages rather than assumed:

1. **`prisma.config.ts` is mandatory for migrations and datasource configuration.** `datasource.url` (and `shadowDatabaseUrl`) no longer live in `schema.prisma`'s `datasource` block — they are read from a config file at generate/migrate time. Verified by running a scratch `prisma init --datasource-provider postgresql --with-model` and inspecting the generated `schema.prisma` (no `url` field in the `datasource` block) and `prisma.config.ts` (contains `datasource: { url: process.env["DATABASE_URL"] }`).
2. **Two datasources require two config files, selected via `--config`.** Confirmed via `prisma migrate diff --help` and the official Prisma config reference documentation (fetched during implementation), which explicitly documents `--config <path>` as the mechanism for non-default config file locations, including in monorepo subpackages.
3. **The generator provider is `prisma-client`, not the legacy `prisma-client-js`.** This is the new default, Rust-free client. `prisma init`'s scratch output confirmed the generator block Prisma now writes by default is `provider = "prisma-client"`.
4. **An explicit `output` path is now required in the generator block.** Prisma Client is no longer generated into `node_modules` implicitly. This implementation outputs to `src/generated/postgresql` and `src/generated/sqlite` respectively (gitignored, regenerated by `db:generate`).
5. **The generated client requires an explicit driver adapter at construction time**, not a bare connection string. Verified directly by reading the generated `internal/prismaNamespace.ts`'s `PrismaClientOptions` type, which types `adapter` as **required** (`adapter: runtime.SqlDriverAdapterFactory`) unless using Prisma Accelerate (`accelerateUrl`) instead. This is the reason `@prisma/adapter-pg` + `pg` and `@prisma/adapter-better-sqlite3` + `better-sqlite3` were added as real runtime dependencies, not just dev tooling.
6. **`prisma migrate diff --from-empty --to-schema=<file> --script` requires no live database connection.** Verified by successfully running it against the PostgreSQL schema with no PostgreSQL server reachable anywhere in this environment — confirming this is the correct mechanism for authoring an initial migration offline, and that Prisma 7 preserved this capability (flag names `--from-schema-datasource`/`--to-schema-datasource` were renamed to `--from-config-datasource`/`--to-config-datasource` in v7, but `--from-empty`/`--to-schema` were not renamed or removed).
7. **Migrations must live next to the schema file that owns the `datasource` block**, not in a shared top-level `migrations/` folder, when using multiple schemas. This is why `prisma/postgresql/migrations/` and `prisma/sqlite/migrations/` are separate directories rather than one shared `prisma/migrations/`.
8. **Seeding is no longer automatic.** Prisma 7 only runs a seed script on explicit `prisma db seed`, never implicitly after `migrate dev`/`migrate reset`. Not used in M2 (no seed data was requested), but noted here since it affects future milestones that may add seed scripts.

## 5. Every Deviation from the Original Architecture and Justification

| # | Deviation | From what | Justification |
|---|---|---|---|
| 1 | Implemented **Option A** (two full schema/config/migration sets) instead of the M2 planning report's **recommended Option C** (PostgreSQL-only, SQLite deferred to M11) | `docs/meeting-notes/M2-planning-report.md` §9 | This M2 implementation request explicitly listed **"SQLite preparation"** as an in-scope deliverable, which is broader than Option C. Additionally, this sandboxed environment has no Docker/PostgreSQL/`psql` (confirmed by direct `which` checks before implementation began), while SQLite works immediately with zero external infrastructure — making SQLite the only datasource that could be end-to-end *proven* here. Both reasons are environment/scope-driven, not a reversal of the planning report's reasoning about long-term maintenance cost (see Risk 2 in Section 8, which restates that cost explicitly). |
| 2 | Two `prisma.config.*.ts` files at the package root, not anticipated by the planning report | Planning report assumed Prisma 6-era single-schema-with-embedded-`datasource.url` semantics | Prisma 7's mandatory config-file architecture (Section 4, point 1–2) makes this structurally required, not a design choice — there is no supported Prisma 7 way to keep two datasource URLs inside `schema.prisma` files anymore. |
| 3 | Added `@prisma/adapter-pg`, `pg`, `@prisma/adapter-better-sqlite3`, `better-sqlite3` as production dependencies | Not mentioned anywhere in the frozen v3 architecture or the M2 planning report | Required by Prisma 7's driver-adapter-only client construction (Section 4, point 5). This is a consequence of the Prisma version installed, not a discretionary architectural addition. |
| 4 | `infra/env/.env.example` and `.env.test.example`: `SQLITE_PATH` → `SQLITE_URL` | Original scaffold (M0) placeholder name | The original placeholder was never wired to anything (Prisma had not been initialized yet). Renamed to match the actual environment variable name consumed by `prisma.config.sqlite.ts` and `src/sqlite.ts`, to avoid a dead/misleading placeholder sitting alongside the real one. |
| 5 | No `infra/docker/docker-compose.yml` created, despite the planning report suggesting one | Planning report §8 ("New root/workspace-level additions needed") | This implementation request's explicit scope list did not include it. Left for M3 (or whenever a real local/CI PostgreSQL instance is actually needed to run `db:migrate:postgresql:deploy`). |
| 6 | `Studio.name` is `String @db.VarChar(120)` in PostgreSQL but plain `String` in SQLite (no length attribute) | N/A — matches the planning report's own anticipated risk | Not really a deviation — this was explicitly flagged as the expected handling in the M2 planning report (§10, Risks) and implemented exactly as predicted there: SQLite has no enforced varchar length, so the attribute is simply omitted in that schema. No changes were made to the frozen v3 monorepo architecture itself (folder structure, package boundaries, or Next.js/Tauri/NestJS technology choices) — all deviations above are internal to `packages/database`'s implementation details and environment/tooling realities discovered during this milestone.

## 7. Remaining Issues

1. **A `pnpm install` mid-session unexpectedly prompted interactively** ("The modules directories will be removed and reinstalled from scratch. Proceed? (Y/n)"), which is not scriptable/CI-safe as invoked. It was resolved by re-running with `CI=true pnpm install`, which completed a full clean reinstall successfully. The root cause was not fully diagnosed (likely pnpm detecting an inconsistency between `pnpm-lock.yaml` and the on-disk `node_modules` state after several incremental `pnpm add` calls in one session); it is not believed to be specific to this package, but it is a reproducibility rough edge worth a maintainer's attention before this is relied on in CI.
2. **The PostgreSQL migration has never been applied to a real PostgreSQL server.** It is schema-correct by construction (generated by Prisma's own offline diff engine, not hand-written), but "generated correctly" and "proven to apply cleanly" are not the same claim. This should be the first thing done once a real PostgreSQL instance exists (M3, or a local Docker instance).
3. **`better-sqlite3`'s native addon build showed one anomalous log line** during compilation (`/bin/sh: Area/ST-MANAGER/node_modules/.../lib.host:/Users/admin/Work: No such file or directory`), caused by the workspace path containing a space (`Work Area`) reaching an unquoted shell context inside `better-sqlite3`'s own build scripts. The build **completed successfully anyway** (confirmed via exit code `0` and a working `prisma migrate dev` run against it afterward), but this is a latent fragility: a future `better-sqlite3` version, or a different native dependency with less defensive build tooling, could fail outright on a path containing spaces.
4. **`prisma generate` intermittently required elevated sandbox permissions** in this session — one invocation failed with `EPERM: operation not permitted, utime '.../.cache/prisma/...'` (a shared, outside-workspace cache directory) and needed to be retried with broader filesystem permissions to succeed. This is an artifact of this sandboxed execution environment, not of the Prisma setup itself, but is worth noting in case it recurs in other sandboxed/CI contexts with similar filesystem isolation.
5. **No `infra/docker/docker-compose.yml` exists yet** (Section 5, deviation 5) — needed before `db:migrate:postgresql:deploy` can be exercised locally.

## 8. Risks

- **Dual-schema maintenance cost (restated from the planning report, now actually incurred).** Every future schema change (as early as M5) must be authored in both `prisma/postgresql/schema.prisma` and `prisma/sqlite/schema.prisma`, with both migration histories kept in step manually. No tooling enforces this synchronization today.
- **PostgreSQL path is unverified against a live server** (Remaining Issue 2) — treat the generated migration as a strong draft, not a proven artifact, until applied for real.
- **Native dependency fragility on this workspace path** (Remaining Issue 3) — `better-sqlite3` is the first native (compiled) dependency in the repository; prior packages were all pure JS/TS.
- **SQLite is not consumed by anything yet**, consistent with ADR 0001. If ADR 0001's M11 follow-up chooses Rust-native SQLite (`rusqlite` — still the stated "current lead candidate") instead of Prisma-on-SQLite, this SQLite schema/client/migration would not be reused directly by `apps/desktop`, though it would still serve local API development in the meantime.
- **Sandbox filesystem-permission inconsistency for `prisma generate`** (Remaining Issue 4) could recur in other constrained execution environments (e.g., certain CI runners) and should be tested there before assuming it "just works."
- **No automated CI yet** (unchanged since M0+M1) — every validation in this report was run locally, once, in this session.

## 9. Why the Root `pnpm typecheck` Still Fails

**Root cause: 11 of the repository's 19 packages/apps still contain zero real `.ts`/`.tsx` source files** — they are exactly as scaffolded in M0, with only `.gitkeep` placeholders inside `src/`. `tsc --noEmit` hard-fails with `TS18003: No inputs were found in config file` whenever a tsconfig's `include` pattern (`["src"]`) resolves to zero files, which is unavoidable for a package that has not started implementation yet.

This was independently verified in this session by counting real source files in every candidate package:

```
apps/api: 0 .ts/.tsx files        packages/api-sdk: 0 .ts/.tsx files
apps/web: 0 .ts/.tsx files        packages/contracts: 0 .ts/.tsx files
apps/desktop: 0 .ts/.tsx files    packages/events: 0 .ts/.tsx files
packages/ai: 0 .ts/.tsx files     packages/logging: 0 .ts/.tsx files
                                   packages/storage: 0 .ts/.tsx files
                                   packages/theme: 0 .ts/.tsx files
                                   packages/ui: 0 .ts/.tsx files
```

...and by running `turbo run typecheck --continue` (which does not stop at the first failure), which failed exactly these same 11 packages and no others.

**This is not new in M2** — it has been true since the M0+M1 implementation report, which already documented this exact failure mode for empty packages and treated it as expected/by-design (that report validated only the four foundation packages that had real code at the time: `types`, `constants`, `utils`, `validation`). M2 added a fifth package with real code (`@st-manager/database`), which typechecks cleanly, both in isolation and as part of the full build. **The default (non-`--continue`) `turbo run typecheck` reports only the first failure it encounters, and which package that is varies between runs** (this session saw it report `@st-manager/storage` on one run and `@st-manager/ai` on another, purely due to turbo's parallel task scheduling) — the underlying set of 11 failing packages is deterministic even though which one is *shown first* is not.

In short: **the root typecheck does not fail because of anything M2 changed.** It fails because 11 packages have not reached the milestone where they get real source code yet (M3 for `api`, later milestones for `web`/`desktop`/`ui`/etc., per the roadmap). `packages/database` itself — the subject of this milestone — typechecks cleanly both alone and inside the full monorepo build/typecheck graph.

## 10. Whether the Project Is Safe to Proceed to M3

**Yes, with two specific follow-ups to carry into M3 rather than block on:**

1. `packages/database`'s PostgreSQL path (schema, client, and generated migration SQL) is real, generated, and type-correct, but **has never been applied to a live PostgreSQL server**. M3 (NestJS API bootstrap) is the natural place to provision a real local/CI PostgreSQL instance and run `pnpm --filter @st-manager/database run db:migrate:postgresql:deploy` for the first time — this should be one of M3's first steps, not an afterthought, since it is the one part of M2 that could not be fully proven in this environment.
2. The `pnpm install` interactive-prompt issue (Remaining Issue 1) should be re-tested at the start of M3 to confirm it does not recur; if it does, it should be root-caused before any CI pipeline (M13) is built on top of `pnpm install` running non-interactively.

Everything else validates cleanly and is not a blocker:
- `packages/database` builds, typechecks, and lints with zero errors in isolation and as part of the full workspace graph.
- The SQLite path is proven end-to-end (real migration, real applied schema, real `migrate status` confirmation) — strong evidence the schema design itself (the `Studio` model, the dual-config approach, the generated-client wiring) is sound, independent of which specific database engine is behind it.
- The repository-wide `pnpm typecheck` failure is fully explained, pre-existing since M0, unrelated to M2, and does not indicate any defect in this milestone's work.
- No scope violations: no auth, users, roles, permissions, API/controller/service, AI, or offline-sync code was written.

**Recommendation: proceed to M3**, with its first task being provisioning a real PostgreSQL instance and applying the M2 migration against it before building the first NestJS module on top of `packages/database`.
